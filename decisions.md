# decisions.md — Study Streak App

Log every meaningful technical decision here: what was decided, why, and what alternative was considered. Keeps future sessions from re-litigating settled questions or silently drifting from the plan.

---

| Date | Decision | Rationale | Alternative considered |
|---|---|---|---|
| Planning | React Native (Expo) for mobile | Cross-platform, reliable local notification scheduling, reuses JS skillset | PWA — rejected because local notification reliability is weak, especially on iOS |
| Planning | Backend required (not fully local) | Streak must be server-verified to be tamper-proof; also protects data if phone is lost | Fully local with AsyncStorage only — rejected, streak could be gamed via device clock change |
| Planning | Strict streak: reset entirely on a missed day | Explicit user decision | Forgiving streak with grace days — considered but not chosen |
| Planning | Day completion threshold = 3 of 4 blocks | Explicit user decision — balances strictness with small real-world slack | All 4 required — considered too rigid given the strict reset already in place |
| Planning | JWT + bcrypt auth, single user, no RBAC | Reuses proven pattern from Team Task Manager project; RBAC unnecessary for one user | — |
| Planning | Notification copy is factual, never guilt-based | Matches the project's own principle of avoiding dark patterns | — |
| Planning | EAS Build → APK, no Play Store submission required | Personal single-device use, avoids store review overhead | Play Store listing — unnecessary for this use case |
| Planning | Phase 9 (device testing) and Phase 10 (build/deploy) require explicit human confirmation | Same safeguard used on Dark Pattern Detector — prevents premature shipping | — |
| Phase 1 | Cron library: `node-cron` (v4) | Already in the dependency list from SETUP.md, lightweight, works for a single daily schedule | `node-cron` alternatives like `cron` — not needed for a fixed midnight job |
| Phase 1 | DB connection in `src/config/db.js`, exported for `server.js` | Keeps app.js (testable, DB-agnostic) separate from startup; supertest tests won't need a live DB | Connecting inline in app.js — rejected so the app module stays importable without DB |
| Phase 1 | `streakCalculator.js` is pure/non-mutating — returns a new state object + `streakChanged` flag | Keeps the core logic fully isolated and trivially unit-tested; flag lets the caller skip DB writes when nothing changed | Mutating shared state — rejected, harder to test and reason about |
| Phase 1 | JWT expiry 365d, payload `{ userId }` only | Single-user app; minimal token payload per skills/api-design-conventions.md | Short-lived tokens + refresh flow — unnecessary complexity for one user |
| Phase 2 | Integration tests use `mongodb-memory-server` (devDependency) | Endpoint happy-path tests run in-memory, no Atlas credentials required, repeatable on any machine | Hitting the real Atlas DB in tests — rejected (destructive, needs creds, flaky offline) |
| Phase 2 | `POST /logs/:date` implemented as a merging upsert (index-wise OR of `sessionsCompleted`) | Per skills/offline-first-sync.md: a stale offline sync must never turn a `true` back to `false` | Blind overwrite — rejected, would lose check-ins |
| Phase 2 | `GET /roadmap/today` computes the current phase/week from `user.startDate` + elapsed days, clamped past the roadmap end | Matches spec ("day 1 of the roadmap, used to compute today's topic"); graceful beyond the last week | Storing an explicit "current position" on the user — rejected, drifts if days are skipped |
| Phase 2 | Roadmap subdocs (`weeks`, `resources`) get `_id: false` | Pure reference data; avoids leaking subdocument `_id`s into API responses | Keeping auto `_id`s and stripping in the controller — more code for no benefit |
| Phase 2 | `GET /badges` returns stored badges only; earning logic deferred | The Phase 2 contract only requires returning earned badges | Auto-earning badges during streak writes — out of scope, add when Progress screen needs it |
| Phase 2 | Tests set their own `JWT_SECRET` (empty `.env` value breaks jsonwebtoken v9 sign) | Keeps tests independent of developer `.env`; also surfaced that `.env` must have a real secret before running the server | Requiring a populated `.env` for tests — rejected, breaks CI/fresh clones |
| Phase 3 | Aligned mobile deps to Expo SDK 57.0.0 (expo@~57.0.11, RN 0.86.2, react 19.2.3) | The scaffolded package.json was an unresolvable mix of SDK 53 and 57 versions; mobile/AGENTS.md pins SDK 57, and `predictiveBackGestureEnabled` in app.json only exists in SDK 57 | Staying on SDK 53 — rejected, would have required downgrading router/fonts/ui and dropping app.json fields |
| Phase 3 | Expo Router file-based routes (`src/app/`), auth via React context + a `status` machine, not expo-router auth guards | Simple redirects in each protected screen keep the guard logic in one file per screen and avoid a `Stack.Protected` dependency | `Stack.Protected` / route groups with auth guards — added complexity, unnecessary for a single-user app |
| Phase 4 | Pending-sync queue uses per-date AsyncStorage keys (`pending_sync:<date>`) instead of one JSON array | Keys survive restart and are race-free: a check-in that lands mid-flush can't be overwritten/lost by the flush's final write | Single queue array — rejected, the flush's read-then-write could drop a fresh entry |
| Phase 4 | Local checklist is overwritten with the server-merged array on sync, but only when the pending entry is unchanged; streak always comes from `GET /streak` | Follows "server is authoritative once synced" without clobbering a newer unsynced tap; streak is never computed on-device | Always overwrite local state from server — rejected, would erase a just-made offline check during an in-flight flush |
| Phase 4 | Sync triggered on toggle, app foreground, and a 30s interval — no NetInfo dependency yet | Keeps Phase 4 dependency-free; the backend OR-merge upsert already prevents true-to-false regressions | `@react-native-community/netinfo` for instant reconnect flush — deferred to Phase 8 offline hardening |
| Phase 5 | Reminder schedule uses SDK 57 repeating triggers — one **daily** (4:00 wake) + **weekly** triggers per block that encode the day type (Mon–Fri / Sat / Sun) | Weekly triggers with `weekday` inherently know which day they fire on, so nothing needs to reschedule when the day type changes (e.g. no fragile midnight job that must run while the app is open); the daily trigger covers the every-day wake | A single repeating schedule that ignores day type — rejected, would fire weekday reminders on weekends; also considered rescheduling-all on day-type change — rejected, requires the app to be running across day boundaries |
| Phase 5 | `ensureScheduleExists()` only schedules when permission is granted and zero notifications are already scheduled; runs once on sign-in | OS persists scheduled notifications across launches, so rescheduling every launch is unnecessary and risks stacking duplicates; the zero-check self-heals a wiped schedule | Cancel+reschedule on every launch — rejected, redundant OS writes and duplicate risk |
| Phase 5 | Settings exposes a reminders toggle (enable → permission + schedule, disable → cancel-all); a per-block time editor is deferred | Matches the skill's cancel-and-reschedule guidance without shipping a full editor; times are fixed to the study plan and the reschedule helper already exists for when editing lands | Full time-picker editor in Settings — deferred, times aren't user-configurable yet |
| Phase 6 | Heatmap renders a fixed 16-week window (columns = weeks, rows = weekdays, aligned to the Sunday-start week containing today) rather than the full journey | Streak `history` only contains logged days, so the grid is built from a continuous date range; 16 weeks fits a phone width with 14px cells and matches GitHub-style defaults | Full-journey window from `user.startDate` — rejected, the client has no `startDate` and an unbounded range would overflow the screen |
| Phase 6 | Progress screen renders the full fixed badge catalog (all 11) and marks earned vs unearned visually, not just the earned set from `GET /badges` | Per skills/mobile-ui-patterns.md: don't hide unearned badges — seeing what's next is motivating | Showing only `GET /badges` results — rejected per the skill |
| Phase 6 | Badge catalog (labels, descriptions, icons) is a static client-side constant derived from the backend's milestone enum; the server stays the authority on which badges are earned | The milestone enum is a fixed contract (`Badge` model), so the client can render the full set without a catalog endpoint | New `GET /badges/catalog` endpoint — unnecessary, the enum is fixed by the schema |
| Phase 7 | Current-week highlight in the roadmap browser derives from `GET /roadmap/today` (`phaseNumber` + `week`), not from `startDate` on the client | The backend already computes today's phase/week from `user.startDate`; reusing it keeps position logic server-side and avoids exposing `startDate` or duplicating the week-index calculation | Client computing the week index from `startDate` — rejected (would need `startDate` in an API response and duplicate backend logic) |
| Phase 7 | Roadmap browser is a single scrollable list grouped by phase, no drill-in pages | 8 phases / ~20 weeks fits one list; keeps navigation shallow per skills/mobile-ui-patterns.md, and the screen is read-only reference | Per-phase drill-in screens — unnecessary complexity for a read-only reference |
| Phase 8 | Reconnect detection lives in the Today screen (`expo-network` `addNetworkStateListener`), watching the offline→online edge and calling `syncNow()` | It sits next to the other sync triggers (toggle/AppState/interval), so the "Pending sync" label clears immediately after a successful reconnect flush — no global side-effecting module or cross-component event plumbing | Global listener in root `_layout.tsx` + an event bus to wake the Today screen — rejected, more moving parts for a single-user flow where Today is the active screen during check-ins |
| Phase 8 | `syncNow()` short-circuits when the queue is empty and skips network calls while `isConnected === false` | The 30s interval becomes a cheap no-op when there's nothing to flush or when the device is known-offline; the reconnect listener, AppState foreground, and interval together cover every way back online | `isInternetReachable` as the gate — rejected, it's undefined on some platforms and adds false negatives; a failed flush on a captive network just retries on the next trigger |
| Phase 8 | Mobile queue logic unit-tested with jest-expo (`npm test`), `@types/jest` added to tsconfig `types` | AGENTS.md demands tests on the offline layer; jest-expo is the SDK-blessed preset and runs the AsyncStorage official mock; TS 6 needs jest in `types` for the test file to typecheck | No mobile tests — rejected; a separate tsconfig for tests — unnecessary once `types` is set |
| Phase 10 | Backend hosted on Render (free plan), deployed via a `render.yaml` blueprint at repo root with `rootDir: backend` and secrets (`MONGO_URI`, `JWT_SECRET`) as `sync: false` dashboard vars | Declarative service config that the human could drive from the dashboard; secrets never live in the repo | Railway — not chosen (either is fine per stack); fully manual dashboard setup — more error-prone |
| Phase 10 | Atlas Network Access opened to `0.0.0.0/0` | First Render deploy failed on `MongooseServerSelectionError` (Render egress IP not whitelisted); free-tier egress IPs are dynamic so a fixed IP would break again. Access is still gated by the connection-string credentials + JWT | Whitelisting Render's specific IPs — impractical on free tier |
| Phase 10 | Android package id `com.studystreak.app` | Human choice; must be permanent once installed on a device | `com.vishwakarma.studystreak` — considered, not chosen |
| Phase 10 | EAS build via `preview` profile: `buildType: apk`, `distribution: internal`, `cli.promptToConfigurePushNotifications: false` | Deliverable is a directly installable APK (no store); reminders are local-scheduled so no push notification credentials are needed, and the flag stops EAS from asking | Production `.aab` — needs a Play Store submission the user doesn't want |
| Phase 10 | Production API URL baked as the `config.ts` fallback default (`EXPO_PUBLIC_API_URL ?? 'https://study-streak-api.onrender.com'`) | Dev still overrides via `.env.local`; the release APK needs no EAS env plumbing | EAS environment variables per build — more moving parts for a single-user app |
| Phase 10 (post-deploy fix) | `POST /logs/:date` changed from OR-merge upsert to **authoritative overwrite** of `sessionsCompleted`, and the streak is now **recomputed from all daily logs on every write** (`computeStreakFromLogs`) instead of the incremental `applyLog` | Human report: a mistakenly-checked block could never be unmarked because the OR-merge won't let a `false` clear a stored `true`. Overwrite is safe here — single user/single device, and the client already serializes latest-state per date (one pending key, cleared only if unchanged after the POST). Full recompute (not incremental) is required so un-completing a counted day rolls `currentStreak`/`longestStreak`/`lastCompletedDate`/`totalDaysCompleted` back correctly | Keeping OR-merge — would leave unmarking impossible; incremental un-mark in `applyLog` — impossible without the full day history |
